# Roadmap d'implémentation — nc (Nextcloud Sync Client)

Ce document découpe le projet en étapes concrètes avec leur statut, pour permettre à n'importe quel agent (humain ou IA) de reprendre le travail à froid sans avoir à relire tout l'historique de conversation.

## 0. Comment reprendre ce projet à froid

1. Lire `CAHIER_DES_CHARGES.md` (besoin fonctionnel) puis `SPECS.md` (design technique). Ces deux documents sont la source de vérité fonctionnelle/technique — ne pas les recontredire sans mettre à jour ce roadmap en conséquence.
2. Lire la section 2 ci-dessous (« Décisions actées ») pour ne pas re-débattre de choix déjà tranchés.
3. Regarder le tableau de la section 3 pour savoir quelle est la prochaine étape non terminée (`⬜` ou `🟨`).
4. Avant de coder une étape, vérifier ses prérequis dans le tableau — ne pas commencer une étape dont les prérequis sont encore `⬜`.
5. Après chaque étape terminée : mettre à jour son statut ici (`⬜` → `✅`), et ajouter une ligne au journal des décisions (section 5) si un choix d'implémentation non prévu dans `SPECS.md` a dû être fait.

Légende des statuts : `⬜` non commencé · `🟨` en cours · `✅` terminé · `🟥` bloqué (voir note).

## 1. État global actuel

Dépôt Git initialisé et publié sur GitHub (`ymauray/ncsync`), scaffolding de gouvernance en place. **Phase 0 terminée** : solution .NET 10 bootstrappée, `nc --help` liste les 7 commandes (stubs non implémentés). **Phase 1 terminée** : `GitClient` implémenté et testé. **Phase 2 terminée** : `ICredentialStore` (DPAPI / Keychain / Secret Service + repli fichier chiffré) implémenté et testé. **Phase 3 terminée** : `nc config username`/`nc config password` fonctionnels de bout en bout. **Phase 4 terminée** : `NextcloudWebDavClient` (PROPFIND/GET/PUT/DELETE/MOVE/MKCOL) implémenté et testé avec un `HttpMessageHandler` factice, sans instance Nextcloud réelle. **Phase 5 terminée** : `SyncState`/`SyncStateStore` (`.nc/state.json`) implémentés. **Phase 6 terminée et validée en conditions réelles** : `nc clone` fonctionnel contre une instance Nextcloud réelle — PROPFIND récursif, téléchargement, `git init`/`add -A`/`commit`, `.gitignore`, `.nc/state.json`, extension du schéma `.nc/config` (`ServerUrl`, `RemotePath`), refus d'un dossier de destination non vide (comme `git clone`, sauf `.nc/` seul). 88 tests au total, 84 exécutés + 4 skip propres (Keychain/Secret Service, non disponibles sur la machine de dev Windows). Suite à cela, `nc config password` a été aligné sur `nc config username` (identité globale réutilisable, voir journal). **Phases 7, 8, 9 terminées** : `nc add`, `nc status`, `nc diff` — passe-plat direct vers `GitClient.Add`/`Status`/`DiffCached` (Phase 1), vérifiés manuellement. **Phase 9b (ajoutée après coup) terminée** : `nc reset <spec>`, réinitialise des fichiers à partir de `refs/nc/synced` (équivalent local de `git checkout -- <spec>`), suppression locale pour un fichier jamais synchronisé — un bug réel (chemins façon Windows mal gérés par `PathExistsInRef`) a été rapporté en usage réel et corrigé, avec tests de non-régression. `nc status` affiche désormais un message explicite sur espace de travail propre. 125 tests au total, 121 exécutés + 4 skip propres (Keychain/Secret Service, non disponibles sur la machine de dev Windows). Parallélisation xUnit désactivée pour tout l'assemblage de tests (course détectée sur `Console.Out` entre classes de tests, voir journal).

Commandes fonctionnelles à ce stade : `config`, `clone`, `add`, `reset`, `status`, `diff`, `push`. **Phase 10 terminée** : `nc push` (cas nominal, sans conflit ni renommage) fonctionnel — diff staged (`git diff --cached --name-status -M`) → `PUT`/`DELETE` WebDAV selon le statut → ETag relu par `PROPFIND` ciblé après chaque `PUT` → commit + avancement de `refs/nc/synced` + `.nc/state.json`, tout-ou-rien côté état local en cas d'échec réseau en cours de batch. **Phase 11 terminée** : détection de conflit par ETag (SPECS.md §4) — avant toute écriture, chaque fichier modifié/supprimé/renommé déjà connu de `.nc/state.json` est vérifié par un `PROPFIND` ciblé comparant son ETag distant actuel à celui enregistré (une disparition — 404 — compte aussi comme conflit) ; un écart annule tout le batch (`NcPushConflictException`, aucune écriture, y compris pour les fichiers non conflictuels du même batch). **Phase 12 terminée** : les renommages Git sont désormais mappés vers un vrai `MOVE` WebDAV (`OldPath` → `Path`, ETag relu par `PROPFIND` après le `MOVE`) plutôt que refusés — la vérification de conflit porte sur l'ETag connu de `OldPath`. 154 tests au total, 150 exécutés + 4 skip propres. `nc push` est maintenant complet pour son périmètre (SPECS.md §4 et §8.3). Reste à faire : `pull` (Phases 13-14), chunked upload (Phase 15), gestion d'erreurs fine sur échec partiel (Phase 16).

Prochaine étape : **Phase 13 — commande `nc pull` (cas nominal)**.

## 2. Décisions actées (ne pas rouvrir sans raison documentée)

| Sujet | Décision | Réf. |
|---|---|---|
| Interface Git | Shell-out vers le binaire `git` (`Process`), pas de LibGit2Sharp | SPECS.md §2 |
| Transport serveur | WebDAV natif (`HttpClient` + verbes custom), pas de lib WebDAV tierce | SPECS.md §3 |
| Cibles OS | Windows, macOS, Linux dès la v1 | CAHIER_DES_CHARGES.md §6 |
| Fusion | Aucune — conflit = refus explicite, jamais de merge automatique | CAHIER_DES_CHARGES.md §5, SPECS.md §4 |
| Périmètre commandes | `config`, `clone`, `add`, `reset`, `push`, `pull`, `diff`, `status` — pas de `branch`/`tag`/`merge`/`rebase`/multi-remote | CAHIER_DES_CHARGES.md §4 |
| Credentials | Abstraction `ICredentialStore` : DPAPI (Windows) / Keychain via `security` (macOS) / `secret-tool` + repli fichier chiffré (Linux), sélection via `OperatingSystem.IsXxx()` | SPECS.md §5 |
| Identité globale vs config locale | `nc config username`/`password` écrivent une identité globale (`~/.config/ncsync`, `CredentialKey.Global`) réutilisable pour tout futur `nc clone` ; `.nc/config` + `CredentialKey.ForPath(dossier)` restent locaux, propres à chaque dossier cloné (`ServerUrl`/`RemotePath` inclus) | SPECS.md §5 |
| CLI framework | `System.CommandLine` | SPECS.md §6 |
| Nommage projets | Solution `ncsync.slnx`, projet CLI `Nc/Nc.csproj` (namespace `Nc`, `AssemblyName=nc`), tests `Nc.Tests/Nc.Tests.csproj`, réf. via `InternalsVisibleTo` | Journal §5, entrée 2026-08-27 |
| Version System.CommandLine | Épinglé en `2.0.11` (stable), pas la ligne preview `3.0.0-preview.*` qui s'installe par défaut avec `dotnet add package` | Journal §5, entrée 2026-08-27 |

## 5. Journal des décisions d'implémentation

*(à compléter au fil du développement — une ligne par choix non prévu dans SPECS.md mais nécessaire pour avancer)*

| Date | Décision | Raison |
|---|---|---|
| 2026-08-27 | Un seul projet CLI (`Nc`) plutôt qu'une séparation CLI/Core dès le départ ; `GitClient`, `NextcloudWebDavClient`, `SyncState`, `ICredentialStore` vivront comme classes internes du même projet, exposées aux tests via `InternalsVisibleTo` | Pas de consommateur externe de la logique métier prévu — éviter une abstraction (séparation en assemblies) non justifiée par un besoin actuel |
| 2026-08-27 | `System.CommandLine` épinglé à la version stable `2.0.11` | `dotnet add package` installe par défaut la ligne preview `3.0.0-preview.*`, à l'API différente et non stabilisée ; `2.0.11` est la dernière stable, alignée avec `ymauray/johannes` |
| 2026-08-27 | Commandes non implémentées de la Phase 0 retournent un message explicite sur stderr + code de sortie 1 (fonction `NotImplemented`) plutôt que de planter ou de ne rien afficher | Rend l'état d'avancement visible directement en ligne de commande, cohérent avec le statut `ROADMAP.md` |
| 2026-08-27 | Solution au format `ncsync.slnx` (nouveau format XML sans GUID), généré par défaut par `dotnet new sln` sous .NET 10 SDK — diffère du `.sln` classique de `ymauray/johannes` (généré sous un SDK antérieur) | Format par défaut de l'outillage .NET 10, plus lisible ; les deux formats sont interchangeables et pleinement supportés par le SDK |
| 2026-08-27 | `GitClient.Commit` passe systématiquement `-c user.name=nc -c user.email=nc@localhost` au lieu de compter sur la config git globale de l'utilisateur | Les commits de `nc` sont des points de synchronisation techniques, pas des contributions attribuables ; garantit que `push`/`pull`/`clone` fonctionnent même sans identité git configurée (ex. CI, machine fraîchement installée) |
| 2026-08-27 | `GitClient` n'a qu'une seule méthode privée nommée `Run` (instance) et une méthode statique renommée `RunGit` (au lieu de deux surcharges `Run`) | Deux surcharges `Run` (une d'instance à 1 paramètre `params`, une statique à 2 paramètres dont un `params`) créaient une ambiguïté de résolution de surcharge silencieuse : `Run("init")` était résolu vers la statique avec `workingDirectory="init"` plutôt que vers l'instance — bug détecté par les tests (`Init()` échouait systématiquement) |
| 2026-08-27 | La vérification `git --version` au démarrage (message d'erreur + lien d'installation par OS) n'est **pas** encore branchée dans `Program.cs` à l'issue de la Phase 1 | `GitClient.GetVersion()` existe et est testé, mais son intégration dans l'UX du CLI est repoussée aux phases où les commandes appellent réellement `GitClient` (6 et suivantes), pour ne pas coupler la Phase 1 à des choix de présentation pas encore nécessaires |
| 2026-08-27 | Extraction de `ProcessRunner`/`ProcessResult` (namespace `Nc.Processes`), génériques, à partir du wrapper `Process` initialement privé à `GitClient` | La Phase 2 introduit un deuxième et un troisième consommateur de shell-out (`security`, `secret-tool`) ; dupliquer la logique de capture stdout/stderr aurait été une redite directe. `GitClient` a été mis à jour pour utiliser `ProcessRunner` sans changer son API publique |
| 2026-08-27 | Sélection de plateforme via `OperatingSystem.IsWindows()/IsMacOS()/IsLinux()` plutôt que `RuntimeInformation.IsOSPlatform(...)` mentionné dans SPECS.md §5 | Équivalent fonctionnellement, mais `OperatingSystem.IsXxx()` est le pattern reconnu par l'analyseur de compatibilité de plateforme intégré (`CA1416`) pour garder `DpapiCredentialStore` (annoté `[SupportedOSPlatform("windows")]`) utilisable sans avertissement de build depuis `CredentialStoreFactory` |
| 2026-08-27 | `CredentialKey.ForPath` dérive la clé de stockage d'un secret à partir du chemin absolu (normalisé, insensible à la casse sur Windows) du dossier de travail, hashé en SHA-256 | Non spécifié explicitement dans SPECS.md : un secret doit être associé à un dossier `nc` précis (un dossier = un serveur, cf. CAHIER_DES_CHARGES.md §5), pas stocké sous une clé globale unique qui collisionnerait entre plusieurs clones sur la même machine |
| 2026-08-27 | Sur Linux, le choix entre `SecretToolCredentialStore` et le repli `EncryptedFileCredentialStore` se fait une seule fois à la construction (sonde `secret-tool lookup` sur une clé sentinelle), pas par un essai/repli à chaque opération | Plus simple qu'un décorateur avec repli par appel, et cohérent avec la formulation de SPECS.md §5 (« si aucun trousseau n'est disponible ») qui décrit une condition d'environnement stable, pas une bascule dynamique |
| 2026-08-27 | macOS n'a **pas** de repli fichier chiffré : si `security` est absent, `KeychainCredentialStore` échoue avec une erreur explicite plutôt que de dégrader silencieusement vers `EncryptedFileCredentialStore` | `security` fait partie de macOS de base (contrairement à `secret-tool`, qui nécessite un paquet `libsecret-tools` et un trousseau actif, absents par défaut sur beaucoup de distributions Linux headless) ; son absence signalerait un environnement anormal qui mérite un échec visible plutôt qu'un repli silencieux vers une sécurité moindre |
| 2026-08-27 | `KeychainCredentialStore.Save` passe le secret en argument (`-w <secret>`) à `security`, faute d'option stdin sur `add-generic-password` | Limitation connue et documentée en commentaire dans le code : le secret est brièvement visible via `ps` pour d'autres utilisateurs locaux de la machine. `SecretToolCredentialStore`, lui, transmet le secret par entrée standard (`secret-tool store` le lit sur stdin), donc sans cette exposition |
| 2026-08-27 | `.nc/config` (JSON via `System.Text.Json`) ne contient pour l'instant que `Username` ; les champs serveur/chemin distant ne sont pas encore modélisés | `nc config` s'exécute avant `nc clone` (cf. CAHIER_DES_CHARGES.md §3) : le serveur n'est pas encore connu à cette étape. Le schéma sera étendu à la Phase 6 quand `nc clone` aura besoin d'y écrire ces champs — éviter d'anticiper une forme non encore nécessaire |
| 2026-08-27 | `nc config username/password` opèrent sur `Environment.CurrentDirectory` (pas de paramètre de dossier explicite sur ces sous-commandes) | Reproduit fidèlement le workflow illustré dans CAHIER_DES_CHARGES.md §3 : `nc config` puis `nc clone ... .` s'exécutent depuis le même répertoire courant, qui devient le dossier `nc` une fois le clone effectué |
| 2026-08-27 | `Console.OutputEncoding = Encoding.UTF8` ajouté au tout début de `Main` | Sans ce réglage, les caractères accentués des messages en français du CLI s'affichaient mal (page de code par défaut de la console Windows) — constaté lors du test manuel de bout en bout de la Phase 3 |
| 2026-08-27 | Logique métier des commandes extraite dans `Nc/Commands/ConfigCommandHandlers.cs` (méthodes statiques testables), `Program.cs` ne fait que câbler `System.CommandLine` vers ces méthodes | Permet de tester `SetUsername`/`SetPassword` unitairement sans passer par le parsing CLI ; `Program.cs` reste un pur branchement, cohérent avec le pattern à reproduire pour les commandes des phases suivantes |
| 2026-08-27 | `nc config username`/`password` : argument rendu optionnel (`ArgumentArity.ZeroOrOne`). Sans argument, `username` affiche la valeur enregistrée (rien si aucune) ; `password` ne fait rien et ne affiche rien, y compris si un mot de passe est déjà enregistré | Demande explicite de l'utilisateur après test manuel de la Phase 3. Le mot de passe ne doit jamais être affiché en clair, y compris indirectement (confirmer sa présence serait déjà une fuite d'information) ; `username` n'a pas cette contrainte |
| 2026-08-27 | `NextcloudWebDavClient` prend un `HttpClient` déjà configuré en constructeur (+ une factory `Create(serverUrl, username, password)` pour l'usage réel) plutôt que de construire son propre `HttpClient` en interne | Permet d'injecter un `HttpMessageHandler` factice dans les tests (`FakeHttpMessageHandler`, `Nc.Tests/WebDav/`) sans instance Nextcloud réelle, conformément au livrable de la Phase 4 |
| 2026-08-27 | Parsing du XML `multistatus` PROPFIND extrait dans une classe pure `WebDavPropFindParser` (aucune dépendance HTTP), séparée de `NextcloudWebDavClient` | Testable directement avec de simples chaînes XML représentatives de réponses Nextcloud réelles, sans mock HTTP — complète les tests du client plutôt que de les dupliquer |
| 2026-08-27 | `MoveAsync(fromPath, toPath)` calcule lui-même l'URI absolue du header `Destination` (`new Uri(httpClient.BaseAddress, toPath)`) plutôt que d'exiger que l'appelant la fournisse | RFC 4918 exige une URI absolue dans `Destination` ; le calculer dans le client évite à chaque appelant de dupliquer cette logique et une éventuelle erreur de composition d'URI |
| 2026-08-27 | Piège `Uri.ToString()` vs `Uri.AbsoluteUri` détecté par un test (`BuildBaseUri_EscapesUsername`) : `ToString()` **dé**-échappe le pourcent-encodage pour l'affichage, `AbsoluteUri` conserve la forme échappée réellement envoyée sur le réseau | Les tests de `BuildBaseUri` comparent désormais `.AbsoluteUri`. Le code de production utilisait déjà `.AbsoluteUri` dans `MoveAsync` (correct dès le départ) ; seul le test lui-même utilisait `.ToString()` par erreur — bon exemple de bug qu'un test peut révéler même quand il porte sur une valeur attendue, pas sur le code testé |
| 2026-08-27 | `.nc/state.json` (`SyncState`) ne stocke que `ETagsByPath` ; le point de synchronisation (quel commit local a été poussé) n'y est **pas** dupliqué | Il vit déjà exclusivement dans le ref git `refs/nc/synced` (Phase 1, `GitClient.UpdateRef`/`ReadRef`). Le dupliquer dans `state.json` créerait deux sources de vérité pouvant diverger (ex. `state.json` mis à jour mais ref git non avancé suite à un crash, ou l'inverse) |
| 2026-08-27 | Extraction de `Nc/Storage/JsonFileStore.cs` (générique, `Load<T>`/`Save<T>`) à partir du pattern JSON dupliqué entre `NcConfigStore` (Phase 3) et le nouveau `SyncStateStore` | Deuxième occurrence exacte du même pattern (valeur par défaut si fichier absent, création du dossier parent à l'écriture) — au-delà de deux occurrences ce n'est plus une coïncidence stylistique mais une vraie duplication de logique. `NcConfigStore` refactoré pour l'utiliser, comportement public inchangé (tests de la Phase 3 toujours verts sans modification) |
| 2026-08-27 | `NcConfig` étendu avec `ServerUrl`/`RemotePath` (schéma anticipé au journal de la Phase 3) | `nc clone` doit persister le serveur/chemin distant pour que `push`/`pull` (phases suivantes) sachent où synchroniser sans reparser quoi que ce soit, et pour matérialiser la contrainte « un seul serveur distant par dossier » (CAHIER_DES_CHARGES.md §5) : il n'y a simplement pas de paramètre serveur sur `push`/`pull` |
| 2026-08-27 | `nc clone` lit l'identité (username + mot de passe) depuis `Environment.CurrentDirectory` (là où `nc config` a été exécuté), puis la **recopie** dans le dossier de destination une fois le clone réussi (nouveau `.nc/config` + nouvelle entrée `ICredentialStore` sous la clé du dossier de destination) | Résout un cas non couvert explicitement par CAHIER_DES_CHARGES.md : `destination` peut différer du dossier courant (`nc clone serveur:/chemin autre-dossier`). Sans cette recopie, un `nc push` lancé plus tard *depuis* `autre-dossier` ne retrouverait pas le mot de passe (stocké sous la clé du dossier courant d'origine, différente). Dans le cas usuel (`destination` = `.`), la recopie est un no-op idempotent |
| 2026-08-27 | Algorithme de clone séparé en deux couches : `NcCloneService.CloneAsync` (pur, prend un `NextcloudWebDavClient` déjà construit) vs `CloneCommandHandler.ExecuteAsync` (charge les identifiants, construit le client réel, gère les messages d'erreur utilisateur) | `NcCloneService` reste testable avec un `HttpMessageHandler` factice + un vrai dossier temporaire/dépôt git, sans jamais construire de vraies requêtes réseau ni dépendre du `CredentialStoreFactory` — même séparation de responsabilités que pour `ConfigCommandHandlers` (Phase 3) |
| 2026-08-27 | `Program.cs` converti intégralement en actions asynchrones (`SetAction((parseResult, cancellationToken) => Task<int>)`, `Main` retourne `Task<int>` via `InvokeAsync()`) | La documentation officielle de `System.CommandLine` déconseille explicitement de mélanger actions synchrones et asynchrones dans la même application. `nc clone` a besoin d'async (I/O réseau/disque) ; toutes les autres commandes ont donc été converties aussi, même les stubs `NotImplemented`, pour rester cohérent |
| 2026-08-27 | `PropFindAsync(..., WebDavDepth.Infinity)` utilisé pour récupérer tout l'arbre distant en un seul appel, plutôt qu'une traversée itérative en `Depth: 1` | Plus simple pour une Phase 6 ciblant « des petits fichiers » (cf. livrable). **Limite connue** : certains serveurs WebDAV désactivent `Depth: infinity` pour de gros arbres ; si l'instance Nextcloud réelle de l'utilisateur le rejette, il faudra remplacer par une traversée récursive en `Depth: 1` — à surveiller lors de la validation manuelle de cette phase |
